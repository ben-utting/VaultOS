# VaultOS

This folder is a VaultOS vault: plain markdown files that VaultOS shows as Kanban boards and a Knowledge Base. You work on the files and VaultOS reads them. There is no database and no sync step.

## Boards

Each board is a top-level folder. New work goes on one of these:

<!-- vaultos:boards -->
<!-- /vaultos:boards -->

VaultOS keeps this list current: it rewrites the lines between the two markers when boards change and never touches the rest of this file.

## Layout

```
<Board>/
  _tasks/
    Board.md                generated by VaultOS; never edit it
    _Templates/task.md      copy this to start a job
    _Templates/article.md   copy this to write a finished job's article
  <N. project>/             a project folder, e.g. "2. website"
    <NN-job>/               a job folder, e.g. "03-contact-form"
      task.md               the job: one card on the board
      article.md            the Knowledge Base article, once the job is done
      correspondence/       drafts/, received/, sent/: emails and messages
      data/                 raw material: exports, logs, reports
      diagrams/  screenshots/
```

- `/new-task` creates all of a job's folders (`correspondence/`, `data/`, `diagrams/`, `screenshots/`) up front, so there is always a place to put things.
- One job is one folder with one `task.md`, and shows as one card. Creating the `task.md` is all it takes to put a card on the board.
- Project folders group the cards and are numbered `1.`, `2.` to keep their order. Job folders inside them are numbered `01-`, `02-`.
- A subtask is a numbered folder inside its parent job's folder, with its own `task.md` and a `batch:` key that points at the parent.
- VaultOS does not look for cards in `_tasks/`, `data/` or folders whose names start with a dot.

## Status drives the board

The `status:` line in a task's frontmatter decides its column:

| `status:` | Column | Also set |
|---|---|---|
| `backlog` | Backlog | |
| `in-progress` | In Progress | |
| `blocked` | Blocked | `blocked_by:` what or who it waits on |
| `needs-decision` | Needs Decision | `decision_note:` what needs deciding, by whom |
| `review` | Review | `review_note:` what is left to check |
| `scheduled` | Scheduled | `scheduled_for:` the target date |
| `done` | Done | an `article.md`, unless it is a subtask |

To move a card, change `status:` and set `updated:` to today. Dragging a card in VaultOS changes the same line. VaultOS regenerates `_tasks/Board.md` from these values, so never edit `Board.md` by hand.

Dates are `YYYY-MM-DD`.

### Move the card yourself

The board hides a column while it has no cards, but all seven statuses always exist. When the work changes stage, change `status:` yourself without waiting to be asked, fill the field that goes with it, and add a Progress log line saying why. The column then appears on the board.

- You start working on it: `in-progress`.
- The build or fix is done and the owner needs to check it, test it or read it: `review`, with `review_note:`.
- It waits on someone or something else to act: `blocked`, with `blocked_by:`.
- The owner has a choice to make before it can go on: `needs-decision`, with `decision_note:`.
- It has a date and can't start before then: `scheduled`, with `scheduled_for:`.

Never set `done` yourself. Stop at `review`; `done` happens when the owner says the job is finished (see "Create, split, finish").

## Working on a task

- Read the whole `task.md` first, and again at the start of every session: Goal, Context, Plan, Progress log, Findings.
- Tick Plan items (`- [x]`) as they are done. Add new ones as the work becomes clear.
- Add a dated line to `## Progress log` when something happens, newest at the top: `- YYYY-MM-DD — what happened.`
- Record anything a later session must not have to work out again under `## Findings / decisions`.
- Keep `status:` true to where the work stands.
- Keep the job's files in its folder.

Before you stop, if the task's `status:` is `in-progress` or `review`: make sure its Progress log has today's entry and `updated:` is today. Claude Code gets both rules from hooks in `.claude/` (the task.md is loaded into every prompt, and stopping is held back once while `updated:` is stale); every other agent follows them from here.

## Search the vault before you answer

Before answering a question or starting a job, search what is already known:

    vault-search <words>                 # ranked: newer and curated first
    vault-search <words> --kind article  # Knowledge Base articles only

Open the top hits that bear on the request. Prefer an article's findings over older task notes, and newer over older when they disagree.

## Create, split, finish

Each has a step-by-step guide that works with any coding agent:

- New work: `.vaultos/guides/new-task.md`
- Split a job into subtasks that run in parallel: `.vaultos/guides/new-subtask.md`
- Finish a job: `.vaultos/guides/done.md`

Agents that read `.claude/commands/` (Claude Code, the Cursor CLI) also have them as `/new-task`, `/new-subtask` and `/done`.

## Knowledge Base

A finished job gets an `article.md` next to its `task.md`, written from `_tasks/_Templates/article.md`. VaultOS's Knowledge Base shows every `article.md`. Link articles with `[[<Board>/<N. project>/<NN-job>/article|Label]]`; backlinks appear automatically.

## Skills

Skills live in `.agents/skills/`, which Pi, the Cursor CLI, Codex and most other agents read, with the same copy in `.claude/skills/` for Claude Code:

- `diagram-design`: diagrams (architecture, flowcharts, timelines and more) as self-contained HTML/SVG, in VaultOS colours. Put them in the job's `diagrams/` folder.
- `stop-slop`: strips AI-sounding phrasing from writing. Use it on articles and anything a person will read.

Optional skills sit switched off in `.vaultos/optional-skills/`. To turn one on, copy its folder into both `.agents/skills/` and `.claude/skills/`; to turn it off again, delete both copies.

- `i-have-adhd`: shapes answers for a reader with ADHD: the next action first, numbered steps, short lists.
